### 第三阶段：发现和修复Bug（约60分钟）

#### 步骤6：JsonData出现偏差

#### 步骤7：Lua提取失败
```
问题:
- Lua L循环法找到0个条目（而正则法找到1290）

助手分析:
- Lua BLC的字节布局与假设有偏差
- 需要dump原始字节排查
```

#### 步骤8：精确诊断Bug
```
关键发现:
1. Lua BLC条目结构: \x00 + (nlen=40) + 40字符名 + 8字节nameHash + chunkMd5
2. dot位置与尾部字段不对齐
3. 之前的 find_loop 有bug:
   - tail = blob[dot:dot+66] 从点号开始切片
   - 导致tail向前偏移了扩展名长度
   - chunkMd5校验必然失败

修正:
- tail 从 dot+ext_len 开始
- chunkMd5 从 dot+4+8 起
- 验证: 61E32618B8D6C7A78B20A6D221A4CA90 ✓ 完全匹配
```

#### 步骤9：JsonData v3重提取
```
结果:
- 89959文件
- 0失败
- 91 chunk全对
- JSON有效性 11/300（v4是0/300）

结论: v3正确
```

### 第六阶段：探索Streaming数据（约120分钟）

#### 步骤16：发现VFSAES加密

#### 步骤17：实现VFSAES解密
```
关键发现:

3. blocksInfo 应在 off48

结果:
- VFSAES 解密 + LZ4 解压成功
- 9257字节 blocksInfo 完整解出
```

#### 步骤18：验证CAB文件
```
发现:

```

#### 步骤19：提取Mesh数据
```
铁证如山:
- Mesh 名称: S_monster_boss_nefarp2_body_02_lod2
- 完整资源清单: 52个Mesh、423个GameObject、32个Texture2D、52个SkinnedMeshRenderer

顶点分析:
- stride=16B（pos 12B + 4B间隙）
- uv在独立stream
```

#### 步骤20：探索地形数据
```
发现:
- fb_* 实为特效/物体流
- 真正地面在 Terrain 组（LAYER_C/D/N_* 带 TRET 魔数）
- TRET 是高度定制的专有压缩格式

进一步发现:
- 数据是 24位值流
- 块偏移表存在
- 顶点+索引混合存储
```

#### 步骤21：解析StreamingChunkData
```
重大突破:
- @0x00 就是指向 Global 数据池的偏移
- StreamingChunkData_Global_0_0.bytes = 680124B（真正的Streaming网格数据池）
- InitChunkData_Global_0_0.bytes = 4056129B（Init数据池）

验证:
- -1_-1 @0x00 = 35648 < 680124 ✓
- -3_-1 @0x00 = 35184 < 680124 ✓
- Init_-2_-2 @0x00 = 1004792 < 4056129 ✓
```

#### 步骤22：逆向TRET压缩格式
```
发现:
- H文件有原始u16高度段但分散
- 可能是行级RLE
- 标记: 00 82/00 80/00 84

块格式:
- 00 82 XX YY [N] [N个u16高度]
- 稀疏存储
- 1_1_1 只有 ~106 个非零高度（4225点中）
```


#### 步骤9：假设索引在尾部（失败）
```

- 索引区不在尾部，而在中部
```

## 核心经验

1. **文档是关键**: 8月5日的探索完全基于文档，没有读外部网络
2. **验证很重要**: 每一步都要验证，文件大小、内容格式、校验和
3. **Bug是常态**: 第一次几乎都会失败，需要精确诊断
4. **逆向思维**: 当解析失败时，重新阅读文档，找关键句
5. **工具选择**: PowerShell有编码问题，Python更可靠
