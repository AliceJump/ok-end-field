# 缘缘庄传菜

独立一次性任务，完成当前经营局的厨房下单和结算。在客栈达到4级、开启三间厨房，并启用祀的上菜、上饮品和结账职责后，先配置厨师与菜单、开始经营并打开厨房界面，再启动任务。

任务每次只下一份菜，优先选择队列较短的厨房，等待队列或缺菜标记反馈后重新识别。按黄色缺菜标记安排制作，原料不足或识别不确定时等待；上下滚动扫描菜单。忽略老饕订单，不负责寻路、配置菜单、提升客栈等级或重复开局，不会自动消耗客源重开。

## 识别依据

界面布局、黄色标记颜色范围、厨房队列圆点与选中页签识别借鉴 [MaaEnd PR #6676](https://github.com/MaaEnd/MaaEnd/pull/6676)，核验的版本为 `a6b3ead2429a86d382be0a8fef6c4831113087c6`，原项目与本项目均采用 AGPL-3.0。未引入 Go 服务或餐品图标资源。

本机已有研究材料中的 `InnUtils.buildFoodDemandMap` 会扣除出餐台、厨房在制/排队与托盘中的同类菜；`InnKitchenOrderingPopUpCtrl._RefreshAllRecipeDemandTags` 仅在剩余需求大于0时显示标记。因此不需要再次识别每桌餐品图标，也不需要按技能推算制作时长和维护虚拟库存。识别反馈异常时重新读取标记，不沿用上次订单快照。

2026-10-20 核对过原始研究 Lua 文件 SHA256，以及当前安装客户端两个 Lua VFS 索引指纹，均与提取记录一致。上述是客户端实现证据，不能据此推断服务器未公开逻辑。

## 分辨率与验证边界

所有坐标以游戏截图为准，将16:9截图归一到1280×720进行颜色识别，点击通过相对游戏坐标映射。拒绝非16:9或小于720p的帧；项目的全局最低分辨率仍为1600×900。

本机2026-10-20实际游戏客户区为1920×1080，Windows DPI为120（125%），电脑工具给出的逻辑截图为1536×864。不能把逻辑截图坐标直接当作1920×1080的像素坐标。

当前账号的活动入口显示尚未完成主线「着新墨」与「开画大吉」，无法进入客栈。已检查解锁条件、真实分辨率与缩放；**厨房坐标、颜色阈值、菜单滚动及整局结算尚未实机验证**。无需新增图像模板；自动化测试仅验证合成图像上的缩放、标记/队列识别以及任务状态边界，不代替实机验收。首轮实现应按实验性任务审阅。
