# 缘缘庄传菜

独立任务，支持自动开局、厨房下单、预备库存和多局结算。需要客栈4级、三间厨房、每间两个厨师位及扩建到8格的出餐台；从缘缘庄柜台的「开始经营」交互点、缘缘本色主题页、营业设定页或经营中的厨房界面运行。

`经营轮次`默认5，范围1到100，客源不足60时提前停止。游戏未运行时复用项目的`ensure_main`启动和登录流程。任务不负责从其他地图寻路到客栈。

自动开局先清空本主题的旧厨师和菜单配置。客户端清空逻辑会把已解锁的祀职责设为启用；随后每间厨房选当前列表前两位干员。按菜单要求选择前N道有原料的菜品和前M种有库存的饮品，每次等待减号选中标记确认，分页搜索去重；不足时停止开局。

经营中每次只下一份菜，优先选择队列较短的厨房，按黄色缺菜标记安排制作。无缺菜时，每道菜单菜品预备两份（包括排队、制作中与已出餐的份数），先覆盖每道菜的第一份再补第二份。本局选菜单时在内存学习图标，只在本局候选中识别桌位餐食；必须完整识别一桌的1或2项点单才建档，出现「用餐中」才扣减一次库存。饮品不计入厨房库存；老饕不作为普通订单识别。无需持久化或新增图标文件。

库存初始状态只对任务刚开的新局可信。接管已在经营的局时不猜现存库存，只按缺菜标记下单。点击后只有明确队列增加才记账；确认失败或旧订单在未观察到用餐前变成另一份订单时，停用本局预制，继续按缺菜标记处理。图标识别不完整时暂停预制，不阻止补菜。

预制最多占7份缓存，为新的实际需求留一个出餐台位置；实际缺菜仍可继续下单。避免先做满冷门菜后，其他菜被满出餐台阻塞。缓存包含排队、制作中、成品与尚未确认用餐的已配送份数，预算宁可高估占用。

## 识别依据

界面布局、自动开局和配置流程、库存策略借鉴 [MaaEnd PR #6676](https://github.com/MaaEnd/MaaEnd/pull/6676)。首轮参考版本为 `a6b3ead2429a86d382be0a8fef6c4831113087c6`，2026-10-23继续对照 `6a5d428d9a9827c6b24a8a6df8d35c783db4b14c`。原项目与本项目均采用 AGPL-3.0。未引入 Go 服务、外部框架或餐品图标资源。

本机已有研究材料中的 `InnUtils.buildFoodDemandMap` 会扣除出餐台、厨房在制/排队与托盘中的同类菜；`InnKitchenOrderingPopUpCtrl._RefreshAllRecipeDemandTags` 仅在剩余需求大于0时显示标记。补菜直接使用游戏标记，预制库存单独记账；不按干员技能或墙钟推算烹饪完成。

2026-10-20 核对过原始研究 Lua 文件 SHA256，以及当前安装客户端两个 Lua VFS 索引指纹，均与提取记录一致。上述是客户端实现证据，不能据此推断服务器未公开逻辑。

## 分辨率与验证边界

所有坐标以游戏截图为准，将16:9截图归一到1280×720进行颜色识别，点击通过相对游戏坐标映射。拒绝非16:9或小于720p的帧；项目的全局最低分辨率仍为1600×900。

本机2026-10-20实际游戏客户区为1920×1080，Windows DPI为120（125%），电脑工具给出的逻辑截图为1536×864。不能把逻辑截图坐标直接当作1920×1080的像素坐标。
