# 角色技能描述与效果 ID 审阅基线

本文档用于审阅 `assets/data/character_skills/*.json` 中的角色技能描述、触发条件与效果 ID。

## 审阅范围

当前审阅分支基于 `origin/master` 提交 `1c9fb3a`。角色技能数据包含：

- 32 个角色 JSON，其中 30 个角色已有技能数据，噗切娜和提弗洛斯暂为空数据；
- 120 条技能记录；
- `EffectType` 中 83 个效果 ID；
- 角色技能 JSON 共引用 55 个效果 ID：53 个出现在技能/条件效果的产出或消费列表，另有 2 个仅用于触发条件。

审阅目标不是给描述中出现的每一个名词机械地添加 ID，而是保证效果 ID 能准确表达自动释放、队伍依赖和技能联动所需要的战斗语义。

## 事实来源优先级

1. `assets/data/i18n_texts/CN.json` 中的当前游戏解包文本；
2. 当前版本游戏内技能描述；
3. 与当前游戏版本匹配的角色 Wiki 页面；
4. 代码注释、旧版 Wiki 和已有人工总结仅作为线索，不可单独作为定论。

外部资料可能滞后；发生冲突时，以当前解包文本和游戏内实测为准。

## 已确认的核心战斗机制

### 物理异常

游戏教程原文键 `33472c3895658295`：

> 当敌人首次受到物理异常时，不会直接触发异常效果，而是进入破防状态。破防状态可以被击飞和倒地叠加（最多 4 层），且会被猛击和碎甲消耗。

据此区分：

- `STATUS_SHRED`：敌人处于破防状态；
- `STACK_SHRED`：破防层数，最高 4 层；
- `STATUS_HEAVY_HIT`：击飞；若目标尚未破防，通常只先施加破防；目标已破防时才触发击飞效果并增加一层破防；
- `STATUS_KNOCKDOWN`：倒地；层数关系与击飞相同；
- `STATUS_HEAVY_STRIKE`：猛击，消耗全部破防层数并按层数造成更高伤害；
- `STATUS_SHATTER`：碎甲，消耗全部破防层数，并按层数提高后续受到的物理伤害；
- “强制击飞/强制倒地”可以绕过“先破防再触发异常”的通常前置条件。

对应解包证据：

- 击飞：`c779efc3851a7c1c`；
- 倒地：`967da1e32464a7db`；
- 猛击：`371c836417c4508f`；
- 碎甲：`e4c0ce945ba5a583`。

### 失衡、重击与处决

- `stagger_value` 表示技能累积的失衡值，不等同于“施加失衡状态”；
- 敌人失衡槽满后进入失衡状态；
- 主控干员此时的普通攻击可变为处决攻击，造成大量伤害并恢复技力；
- 普通攻击描述中的“重击”是攻击序列的终段语义，不能映射为“击飞”。

游戏教程原文键：

- 失衡后处决：`470daeb18aa43882`；
- 技力用途与恢复：`08a7ff3746b4ff56`。

### 法术附着、法术爆发与法术异常

法术附着最多叠加 4 层，并存在两条不同反应路径：

1. 再次施加同类型附着：增加一层附着并产生该类型的法术爆发；
2. 施加不同类型附着：消耗附着并产生法术异常，后施加的元素决定异常类型。

游戏教程原文键：

- 同类附着触发法术爆发：`6cb7047c8090a77f`；
- 后施加元素决定异常类型：`4babaa215ae82cee`；
- 异常等级取决于消耗层数，最高 4 级：`0ad431deefc2c66c`。

四种法术异常：

- `STATUS_BURNING`：其他附着 + 灼热附着；持续受到灼热伤害，原文键 `8741698381a93358`；
- `STATUS_FROZEN`：其他附着 + 寒冷附着；敌人无法行动，受到破防或物理异常时会触发碎冰，原文键 `1fd237f573e5958b`；
- `STATUS_CONDUCTING`：其他附着 + 电磁附着；受到的法术伤害提高，原文键 `dc00c70f6cbbfc88`；
- `STATUS_CORROSION`：其他附着 + 自然附着；所有抗性逐渐下降，原文键 `c95884fcf4cb5d0c`。

### 战斗资源与技能类型

- 技力用于施放战技，会随时间恢复，主控干员重击命中也会恢复技力；
- 终结技使用独立的终结技能量，充满后才能施放，原文键 `deba3a873e665f82`；
- 连携技由角色各自的文本条件触发，并受独立冷却约束；不能仅因为技能造成某个状态，就添加 `TRIGGER_LINK`；
- `spirit_cost` 当前同时承载战技技力消耗和终结技能量需求，审阅时必须结合 `skill_type` 解读。

## 效果 ID 标注规则

### 多条件技能

技能描述中可能同时存在多个相互独立的“当/若/如果”条件。此时使用 `enhancements` 数组逐条记录，不能把所有效果塞进一个 `enhancement`：

- `enhancement`：保留用于兼容旧数据和旧调用方；加载新格式时指向 `enhancements[0]`；
- `enhancements`：完整条件效果列表，每项拥有独立的触发条件和产出；
- 技能发动条件、命中后条件、资源阈值条件和嵌套条件必须分别判断，不能因同处一个描述就合并为 AND；
- 无条件基础产出仍放在 `effects`，不能为了容纳多个条件而移入 `enhancements`。

已确认包含多个条件分支的技能包括萤石「巅峰闹剧」、骏卫「盾卫旗队，上前」、赛希「分布式拒绝服务」、洛茜「燎影时刻」等。

### `effects`

只记录技能实际产生、施加、清除或消耗的结构化结果，不记录：

- 纯伤害类型；
- 描述中仅作为触发前提的状态；
- 普通攻击模板中的“重击”“失衡”“处决”；
- 技能名字或叙述性用词；
- 只存在于连携技触发条件中的状态。

### `enhancement.trigger_condition.effects`

只记录触发条件依赖的状态或层数。必须区分：

- `STATUS_SHRED`：只要求目标已破防；
- `STACK_SHRED`：要求具体破防层数或需要消费层数；
- `ATTACH_*`：要求具体元素附着；
- `STATUS_SPELL_INFLICT`：要求任意法术附着；
- `STATUS_SPELL_ANOMALY`：要求任意法术异常；
- `STATUS_STAGGER`：要求目标已进入失衡状态，不等同于技能造成失衡值。

### `enhancement.effects`

只记录满足触发条件后新增或增强的效果。基础效果与强化效果不得重复承担同一语义，除非运行时确实需要两层表达。

### `enhancement.release_gate`

自动技能 allowlist 只读取显式 `release_gate`，不再从所有 `trigger_condition.effects` 猜测首次施放条件：

- `{"all": [...]}`：同一分支内的效果必须全部有队内先行 producer；
- `{"any": [...]}`：同一分支内任一效果有队内先行 producer 即可；
- 多个 enhancement 分支之间按 OR 判定，但始终保留各自边界；
- `{"static": false}`：阈值、否定条件、命中后/施放后结算等无法由静态队伍产出图安全判断，allowlist 不据此排除普通战技；
- `count < 0` 的消费不是 producer；猛击、碎甲等消费破防层数的异常也不能反推为破防层数 producer；本技能施放后才产生的效果不能反向满足自身首次施放 gate。

### `count`

- 正数：施加或增加；
- 负数：消耗或减少；
- `0`：仅检查/条件引用；
- 未知数量不能默认解释为精确的 `1`；审阅时应尽量从原文确认。

## 已发现的高风险建模点

1. ~~`EFFECT_TERMS` 将“重击”映射到 `STATUS_HEAVY_HIT`（击飞）。~~ 已移除该错误映射，并增加回归测试；普通攻击终段“重击”不再自动产生击飞 ID。
2. `VULN_ALL` 的代码描述是“所有元素伤害增加”，而游戏文案术语是“法术脆弱”。应明确它是否仅指四种法术属性，避免被理解为包含物理伤害。
3. `BUFF_DAMAGE_UP` 被多处用于“额外伤害/追加伤害”的语句；“触发一次额外伤害”通常不是持续伤害增益，需要逐项核对是否应使用 `TRIGGER_ADDITIONAL` 或不标注。
4. 状态“作为触发条件”“被技能消耗”“由技能施加”是三种不同方向；仅凭描述中出现关键词不能决定应放入 `effects`。
5. 击飞和倒地会隐式影响破防状态及层数，但是否同时显式记录 `STATUS_SHRED`、`STACK_SHRED`，需统一规范，不能部分角色显式、部分角色依赖推断。
6. “强制施加燃烧/冻结/导电/腐蚀”直接产生异常，不等同于普通附着；不得同时臆造相应 `ATTACH_*`，除非原文明确也保留附着。
7. `CLEAR_COLD`、`CLEAR_NATURAL` 等按元素拆分的清除 ID 与“消耗所有法术附着”并不完全等价；多元素共存时尤其需要核对。
8. 两个空角色文件不能纳入“技能数据完整”结论。
9. 旧 `skill_database_validation.py` 只做关键词存在性检查，无法证明描述、方向、目标、数量和效果 ID 正确，不能作为 100% 准确的依据。

- 同时保存 `catalog.json`、`char_pool.json`、`weapon_pool.json`、详情页纯文本，以及每名干员对应的完整 `item/list` 关联物品响应（33/33）；
- `manifest.json` 记录每名干员的 item ID、详情 URL、更新时间、文件路径、数据体积、文档组件数量、文件计数以及完整性状态；`latest.json` 只指向最近一次完整抓取。

完整原始 JSON 是后续自动解析倍率和条件的权威 WIKI 输入；纯文本仅用于人工检索，不应替代结构化原始数据。

### 从干净检出复现

Playwright 属于仓库开发工具依赖，不进入主应用运行依赖。仓库现有依赖分组使用 `dev`，因此抓取工具也安装在该组中：

```powershell
git clone https://github.com/AliceJump/ok-end-field.git
Set-Location ok-end-field
git checkout tools/operator-wiki-analysis
uv sync --locked --group dev
uv run --locked python scripts/data-capture/capture_skland_operator_details.py --help
uv run --locked python scripts/data-capture/capture_skland_operator_details.py
uv run --locked python scripts/skill-data/analyze_operator_skills.py
```

抓取器优先启动系统安装的 Chrome（Playwright `channel="chrome"`）。如果系统 Chrome 不存在或无法启动，会回退到 Playwright bundled Chromium。安装 Python 依赖不会自动下载浏览器二进制：系统 Chrome 可用时无需额外安装；只有需要 bundled Chromium 回退时，才运行：

```powershell
uv run --locked playwright install chromium
```

Linux 环境若同时缺少 Chromium 的系统库，可按 Playwright 要求使用 `uv run --locked playwright install --with-deps chromium`，该命令可能需要系统包安装权限。

可用 `--proxy http://127.0.0.1:10808` 指定代理，用 `--headed` 显示浏览器窗口。抓取目录使用秒级时间戳并原子创建；同秒并发会明确报错，不会复用目录混合数据。

抓取结束后会核对原始 catalog 总数、请求子集、失败项、必需全局文件、manifest 条目和实际文件数。失败或 `--limit` 形成的子集快照仍保留用于诊断，并在 `manifest.json` 中写入 `"complete": false` 和 `incomplete_reasons`，但不会覆盖已有 `latest.json`。

### 自动技能分析脚本

`scripts/skill-data/analyze_operator_skills.py` 可直接消费上述官方快照，生成结构化技能审阅数据：

- 提取每名干员的普通攻击、战技、连携技、终结技及完整描述；
- 还原 RANK 1–9、专精 1–3 的倍率、技力、冷却、失衡、持续时间和升级材料二维表；
- 自动识别“当/若/如果”条件，并区分技能发动条件与结算条件；
- 对多个“若……则……”分别建模，不把独立条件错误合并；
- 识别破防、附着、熔火、铁誓、涡流、青霆剑、雷枪等特殊层数/数量及 `>=`、`<=`、精确值；
- 识别“消耗所有”“最后一点”“再次施加该效果”等特殊语义；
- 用 `EFFECT_TERMS` 提出条件和结果的 effect ID 候选；
- 对照本地 `character_skills`，标记描述差异、缺失技能、强化态数量不足和待人工确认项；
- 只生成报告，不自动写回正式角色数据，避免启发式误改。

默认分析读取 `latest.json`，并拒绝 manifest 未明确标记为完整的快照。若要诊断不完整快照，必须同时显式指定快照和允许 partial：

```powershell
uv run --locked python scripts/skill-data/analyze_operator_skills.py --snapshot 20260830_221449 --allow-partial
```

历史样例分析结果（2026-08-30）：33 名干员、127 个技能、64 个条件、9 个多条件技能、16 个特殊层数技能、21 个待复核技能。输出位于：

- `tools/wiki_catalog/operator_details/20260830_221449/analysis/operator_skill_analysis.json`
- `tools/wiki_catalog/operator_details/20260830_221449/analysis/operator_skill_review.md`
