# 滑索与送货逻辑

本文记录滑索（`ZipLineMixin`）和自动送货（`DeliveryTask` / `TakeDeliveryTask`）两个模块的核心思想与逻辑推演过程，供后续开发和维护参考。

---

## 一、总体思路

整个送货自动化可拆分为三个相互独立但顺序依赖的子问题：

1. **抢单**：在委托列表中识别并接取符合条件的委托。
2. **取货**：通过滑索系统到达仓储节点，拾取货物。
3. **送达**：通过滑索系统到达目标 NPC，提交货物完成委托。

三者在设计上各自封装，分别对应 `TakeDeliveryTask`、`to_storage_point_and_back_zip_line()`、`to_end_and_submit()`，由 `DeliveryTask.run()` 统一串联。

---

## 二、滑索系统（ZipLineMixin）

### 2.1 核心问题

滑索有多个连接点，每个连接点对应一个可识别的距离数字（如 14m、108m）。程序无法直接知道"当前哪个连接点在屏幕中央"，只能通过 OCR 扫描当前画面中的数字来判断。

因此，**到达特定连接点**等价于：**将目标距离数字移动到屏幕中心**。

### 2.2 对齐算法

调用 `align_ocr_or_find_target_to_center()`，流程如下：

1. 对屏幕做 OCR，同时用 HSV 颜色过滤器（金色文字 + 白色文字）隔离噪声，提高数字识别准确率。
2. 如果找到目标数字，计算其中心与屏幕中心的偏差 `(dx, dy)`。
3. 若偏差超出容差（默认 50px），向偏差方向移动摄像头，反复迭代直至对齐。
4. 若某次 OCR 未识别到目标（短暂遮挡或帧延迟），利用上一帧的位置做**指数衰减预测**（系数 0.9^N），继续尝试对齐，而不是立即放弃。
5. 若连续多次预测也失败，则进入随机探索，随机移动摄像头重新搜索目标。

这一思路的核心是：**OCR 偶发失败不代表目标消失，先利用历史位置预测，预测失效再重置搜索**，以此在噪声环境中保持鲁棒性。

### 2.3 发射与推进

对齐完成后：

1. 点击连接点（鼠标左键）。
2. 进入循环，**持续按 E 键**，每 0.1 秒检查一次屏幕底部的状态文字。
3. 出现「向目标移动」或「离开滑索架」时，代表本段滑索已触发或完成，退出循环，进入下一段。
4. 单段超时上限为 60 秒，超时则抛出异常，防止卡死。

持续按 E 的原因是：游戏的交互触发窗口很短，程序无法精确预判时机，采用**高频重复输入**来确保不错过触发窗口。

### 2.4 多段序列

配置中每个目的地对应一个距离序列（如 `"14,108,64,109,60"`），代表需要依次对齐并发射的各段连接点距离。程序按顺序逐段执行，全部完成后在最后 `click(key="right")` 完成收尾交互。

## 三、委托接取（TakeDeliveryTask）

### 3.1 核心问题

委托列表是一个多行 UI，每行包含：地点名称、报酬金额、券种图标、接取按钮。程序需要从中筛选出满足条件的委托并点击接取。

难点在于：UI 分三列排布，OCR 结果是无序的坐标散点，需要将它们重新组合为有意义的"行"。

### 3.2 行重建逻辑

策略是找到锚点元素（「查看位置」按钮和「接取运送委托」按钮），以这些锚点在 Y 轴上的分布来切割其他元素，从而重建每一行的归属关系。

具体步骤：

1. 对三个区域（左侧信息区、中间图标区、右侧按钮区）分别做 OCR。
2. 以「查看位置」和「接取运送委托」为行分隔标志，将各自区域的 OCR 结果分组。
3. 以右侧按钮组的 Y 范围为基准，在左侧和中间区域找 Y 轴重叠的元素，合并为一行。
4. 合并后的行元素数量达到阈值（≥5）才视为有效行，构造 `DeliveryRow` 对象。

这样可以在 UI 布局不完全规则、OCR 有漏识别的情况下，尽量正确还原每行的语义。

### 3.3 券种识别

报酬金额文字的上方固定有券种图标（谷地券或武陵券）。识别思路：

1. 以报酬文字的 Y 坐标为下界，向上搜索一个以报酬行高为基准的矩形区域。
2. 对该区域做图像特征匹配（`find_feature`），与两种券种图标模板比较。
3. 若搜索区域因相邻行太近而过小，捕获异常并跳过，避免崩溃。

地点名称同样可以直接区分券种（武陵城 → 武陵券，供能高地等 → 谷地券），作为图标匹配之外的备用判断路径。

### 3.4 筛选与接取

满足条件的委托需同时满足：
- 报酬金额在配置的 `[最低, 最高]` 范围内（上限防止 OCR 误识别的超大数字）。
- 券种与配置的启用项匹配。

找到后点击接取按钮，最多重试 3 次，以「请尽快送达」出现为成功判定依据。

若当前列表无符合条件的委托，则滚动列表查漏，再等待刷新 CD（约 5.6 秒）后点击刷新，循环检测。连续 10 次找不到刷新按钮则判定异常退出，防止无限循环。

## 四、送货任务编排（DeliveryTask）

### 4.1 整体流程串联

`run()` 方法按以下顺序执行一次完整送货：

```
接取委托（other_run）
    ↓
传送至出发点（task_to_transfer_point）
    ↓
滑索前往仓储节点取货（to_storage_point_and_back_zip_line）
    ↓
OCR 识别目标 NPC（常沄/资源/彦宁/齐纶）
    ↓
滑索前往目标 NPC（on_zip_line_start）
    ↓
到达并提交货物（to_end_and_submit）
```

每次循环最多重试 3 次，异常时可配置自动关闭游戏。

### 4.2 目标 NPC 识别

委托接取后，游戏界面会显示目标 NPC 的名称。`run()` 在委托接取后立即 OCR 扫描「送达」按钮旁的文字，从 `["常沄", "资源", "彦宁", "齐纶"]` 中匹配出本次委托的目标，作为后续滑索序列和 NPC 导航的依据。

### 4.3 取货逻辑

`to_storage_point_and_back_zip_line()` 的思路：

1. 等待「登上滑索架」提示出现，点击进入初始滑索。
2. 按配置的「通向送货点」序列滑行。
3. 到达仓储节点附近后，通过方向标识（`secondary_objective_direction_dot`）辅助对齐，步行靠近仓储节点。
4. 检测到「仓储节点」及「取货」提示后点击取货。
5. 取货后等待「登上滑索架」再次出现（如未出现则后退重试），为后续送货滑索做准备。

### 4.4 送达逻辑

`to_end_and_submit()` 在到达目标 NPC 后：

1. 检测 NPC 名称及「提交」等交互提示出现。
2. 点击提交完成委托。
3. 等待结算 UI 消失后返回，准备下一次循环。

### 4.5 功能开关设计

提供「仅接取」和「仅送货」两个开关，方便在调试或特殊场景下只跑流程的某一段，而不必修改代码。「选择测试对象」则允许单独测试某段滑索序列或完整循环，降低调试成本。

## 五、关键设计取舍

| 问题 | 取舍思路 |
|------|---------|
| 滑索对齐为何用 OCR 而非图像特征匹配 | 距离数字随场景变化，OCR 更通用；图标模板维护成本高 |
| 为何持续按 E 而非判断时机后按一次 | 交互触发窗口不可预判，高频输入容错性更强 |
| OCR 失败时为何用预测而非立即重试 | 相机还在移动时目标短暂消失属正常，立即重置会导致震荡 |
| 行重建为何以右侧按钮为锚 | 右侧「接取运送委托」按钮最稳定，是最可靠的行分隔标志 |
| 报酬上限为何设为 100 万 | 游戏内最高不超过 99 万，超出则判定为 OCR 误识别，避免接取异常委托 |
| 刷新为何设 5.6 秒冷却 | 游戏服务端的委托刷新 CD 约为 5.4 秒，留 0.2 秒余量防止刷新失败 |
