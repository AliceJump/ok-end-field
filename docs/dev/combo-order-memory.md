# 战斗内连携顺序表

本层基于已合并的固定四槽识别，在当前战斗内记录头像的相对显示顺序，用于减少后续槽位的模板比较。不接管 E 的调度、连携倍率、技能变体、剩余时间或成功判定，也不修改 PR #489 的释放增益。顺序固定是用户提供的本场优化假设，并非已证明的客户端全局排序规则。

`ComboOrder.before` 保存 `(前面的 native_id, 后面的 native_id)`，从完整队伍候选匹配的实际槽位学习，计算传递关系。只观察到 A/B 不决定 C 的位置，缺失槽不会补位；同一帧重复头像不参与该头像的顺序学习。表里存在一个角色不代表他现在有可用连携，也不能替代当前队首观测。管理员男女仍服从已有编队性别约束，不合并两个原生 ID。

识别流程：

1. 队首始终使用当前队伍完整候选和原 0.80 分数 / 0.08 角色差值门槛。
2. 后续各槽根据本帧左侧实际识别到的头像，排除表里明确位于它们之前的候选。没有关系则保留。相同头像不排除，避免多段技能共用头像时虚构唯一性。某槽未知仍继续后续槽。
3. 缩小后只有分数至少 0.90、缩小范围内的差值至少 0.12 才采用，标为 `match_scope=battle_order`；这些值仍不是概率，也不代表与被排除角色的差值。否则立即用完整队伍重试，不能用旧表填入身份。顺序缩小结果本身不反过来学习新关系。
4. 至少每 0.5 秒进行一次完整候选核验。按 E 后、提示关闭/未知后、尺寸或性别约束变化后，身份缓存清空，下次也完整核验。完全相同的脸部像素和候选集合可以复用既有匹配结果；核验从缩小范围改回全队时不会复用缩小结果。
5. 新的完整匹配若与旧表构成反向关系或传递环，丢弃整张旧表，用本帧重新学习；本帧任何缩小结果也全部完整重试。不能让旧顺序覆盖新的完整图像证据。变化发生到下次完整核验之间，后续槽仍可能受旧提示影响；队首不受此影响。

普通身份缓存清理 `reset()` 保留本场顺序；`reset(clear_order=True)` 同时清空顺序。实际 AutoCombat 入口在已确认的新战斗或非战斗时调用后者，队伍变化也清空。表仅在内存里，不跨战斗、账号或重启持久化；没有新增配置项。布局变化保留同队顺序但强制完整识别。此入口以外直接调用 detector 的工具，应按其自己的战斗边界调用清理。

本 PR 与“连携身份参与伤害排轴”分开：后者应消费当帧队首、遵守 E 只操作队首的约束，不能把本表解释为可任意重排的招式列表。后续槽的 `battle_order` 来源是启发式，应在预测中保留不确定性，实际释放前重新观察队首。原匿名 E 兼容路径和异常隔离不变。

专项覆盖部分顺序、传递、冲突重学、重复头像、未知中间槽、定期核验、身份缓存与顺序表不同生命周期、新战斗/重入/换队。离线合成四槽暖测 120 次：变化像素完整队伍比较中位 7.44 ms / p95 7.67 ms，顺序提示 6.20 ms / p95 7.25 ms；比较数 1904→1552。同像素复用中位 0.044 ms。只测本机产品裁剪及匹配，不含截图、PNG 首次加载、其他调度；这批数值不替代之前实拍测速或现场验证，也不证明四槽实拍准确率。
